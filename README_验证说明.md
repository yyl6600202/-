# 问题二（场景 B）五核方案 · 独立验证说明

**被验证的结论**：在华为杯 A 题「通用神经网络处理器下的多核调度问题」问题 2（场景 B）下，
本方案在 100 个测试用例上取得 **五核算术平均加速比 = 4.1452**（几何平均 3.9704，中位数 4.6490，
最小 1.5462，最大 5.9436，0 个用例失败）。

---

## 0. 验证设计原则（请先读这一节）

**不要运行提交方的求解器来验证结果。** 那样只能证明"提交方的程序自洽"，不能证明结果正确。

正确的验证方式是：**用官方评估器重新模拟提交的方案文件，看能否复现申报的数字。**
本包中的所有脚本都按此原则编写，`verify.py` 除了官方代码之外不导入任何提交方代码
（已把 `claimed_results.csv` 中的全部数字当作"待验证的断言"处理）。

---

## 1. 需要准备什么

只需要一样东西：**题目附件**（`题目附件/`），其下应有 `code/` 与 `data/`：

```
题目附件/
├── code/          ← 官方评估器（multicore_cut_evaluate_problem_2.py 等）
└── data/
    ├── case_001.json … case_100.json   ← 100 个计算图
    └── config.txt                       ← 带宽 60 / L1 524288 / UB 131072 / 场景B延迟 500
```

建议对方使用**自己那份**题目附件（而不是本包附带的副本），这样连"评估器是否被篡改"这一层也一并排除。

`input_hashes.txt` 给出了 100 个计算图、`config.txt`、官方 `code/*.py`
以及本包 100 份方案的 SHA-256，可用于确认双方输入完全一致。校验方式：

```bash
cd <题目附件>
sha256sum data/case_001.json       # 与 input_hashes.txt 第 1 节比对
sha256sum code/multicore_cut_evaluate_problem_2.py   # 与第 2 节比对
```

> Windows 无 `sha256sum` 时可用 `certutil -hashfile data\case_001.json SHA256`。

## 3. 三步验证流程

### 第 1 步 · 快速抽检（约 1 分钟，先确认环境跑得通）

```bash
python verify.py --attachments "C:/path/to/题目附件" \
                 --cases case_002 case_005 case_064 case_100 --workers 4
```

预期输出结尾：

```
  参与复核用例数        : 4（抽检子集）
  官方结构校验通过      : 4
  官方重算与申报不一致  : 0
  单核基线 M1 不一致    : 0
  加速比最大绝对偏差    : 0.000e+00
  ...
结论：PASS —— 官方评估器重算结果与申报数字完全一致
```

### 第 2 步 · 全量复核（100 例，11 进程约 15–40 分钟）

```bash
python verify.py --attachments "C:/path/to/题目附件" --workers 11 \
                 --json-out verify_detail.json
```

脚本对每个用例做四件事：

| 检查项 | 用的官方接口 |
|---|---|
| 方案结构合法（算子覆盖完整 / 子图 DAG / 同核直接依赖保序） | `stub_multicore_cut_and_schedule.validate_multicore_plan` |
| 单核基线 M₁ 重算 | `multicore_cut_evaluate_problem_2.evaluate_scene_b`（1 核） |
| 五核 Makespan M₅ 重算 | `multicore_cut_evaluate_problem_2.evaluate_scene_b` |
| 加速比与聚合量比对 | 与 `claimed_results.csv` / `claimed_summary.json` 逐项比对 |

只有**全部用例结构合法、M₁ 与 M₅ 逐位一致、6 个聚合量一致**时才会打印 `PASS`。
`--json-out` 会写出逐例明细（含每个用例的 M₁、M₅、加速比、子图数、用核数）。

### 第 3 步 · 绕开本脚本，用纯官方命令行抽检

这一步最彻底：完全不用我的任何文件（除了方案本身）。

```bash
cd <题目附件>
python code/multicore_cut_evaluate_problem_2.py \
       data/case_051.json  <verification>/plans_n5/case_051.json \
       --config data/config.txt
```

输出的 `makespan` 应等于 `claimed_results.csv` 中 `case_051` 行的 `makespan`（应为 193319）。

> ⚠️ **注意**：官方 CLI 会在 `data/` 下**写出三个结果文件**
> （`<case>_problem_2_res.json`、`<case>_problem_2_log.txt`、`<case>_problem_2_trace.json`）。
> 若不想污染题目包，请先备份 `data/`，或抽检后手动删除这三个文件。
> （`verify.py` 直接调用 `evaluate_scene_b()`，**不会**产生任何写盘副作用。）

## 4. 口径定义（复现数字前必须统一）

| 项 | 定义 |
|---|---|
| 场景 B 语义 | 每个核心把其所有子图**合并为一个 Task**；同核子图直接复用 L1/UB；跨核依赖经 `COPY_OUT → 500 周期同步 → COPY_IN` |
| **单核基线 M₁** | 全图所有非 COPY 算子放进**同一个子图**、**只用一个核**，用 `evaluate_scene_b` 算出的 makespan |
| **加速比 S** | `M₁ / M₅`，其中 M₅ 为五核方案的 makespan。1 核方案 S ≡ 1 |
| 「五核」 | `core_schedules` 长度为 5（即向评估器提供 5 个核心）；允许某个核心为空（见第 6 节） |
| 固定参数 | 带宽 60 B/cycle；L1 = 524288 B；UB = 131072 B；场景 B 跨核延迟 = 500 cycles |

`verify.py` 中的 `single_core_plan()` 就是上表 M₁ 定义的完整实现（3 行），可直接查阅。

## 6. 已知情况与边界说明（请一并核查）

1. **有 7 个用例的 `core_schedules` 中存在空白核心**：
   `case_035/044/048/064/068/086/088`（分别用 4、2、3、3、4、4、4 个核）。
   这不是 bug：候选池中包含 `column` / `wide` / `continuous` 等**必然切出 5 块**的规则，
   它们在官方评估器下都不优于这些少核解。原因是这些图的单核时间本身只有 1.9 万 ~ 36 万周期，
   而每条跨核依赖要付 500 周期同步延迟，把工作再拆到第 5 个核所引入的同步代价超过并行收益。
   即"5 核可用"不等于"5 核都必须忙"。**若验证方认为必须强制用满 5 核，请明确指出**，
   结论中的均值会相应变化（可重跑并给出强制 5 核版本）。
2. **部分方案沿用问题一的结果。** 100 例中有相当一部分的胜出方案来自
   "把问题一的最优切分直接按场景 B 评估"（内部记作 `warm_start`）——
   这是合法方案，但意味着它同时依赖问题一的正确性。
   `claimed_results.csv` 的 `winner` 列标明了每个用例的方案来源：
   `warm_start` = 沿问题一方案；其余为本次专门为场景 B 生成的切分规则（`column` / `cone` / `chain_wide` 等）。
3. **CSV 编码为 UTF-8 with BOM**，用 `encoding='utf-8-sig'` 读取，否则第一列列名会带 `\ufeff`。

## 7. 如果你想核查的是「算法本身」而不只是「结果」

结果可复现 ≠ 算法无缺陷。若要做算法层面的审查，建议按以下顺序：

1. **读 `问题二算法模型.md`** —— 建模推导、约束、4 个可达下界、CACR 四阶段求解流程、
   复杂度、以及第 9.2 节自己列出的**局限**。
2. **重点质疑三个关键论断**（这是本方案与常规做法差异最大、也最可能出错的地方）：
   - **论断 A**：场景 B 下"同核子图合并为一个 Task"使得子图归属只是"算子→核"映射的编码，
     因而可以一个算子一个子图输出。→ 质疑点：这一编码是否真的与评估器的
     `_prioritize_task_seq`（按子图 rank 做稳定分桶排序）等价？
   - **论断 B**：跨核商图必须无环，否则评估器会以 `dependency cycle` 拒绝。
     → 质疑点：`CostState.try_move` 的环检测是否覆盖了所有增量移动？
   - **论断 C**：对"条带/流水线型"图（如 `case_016/024/051`），
     按拓扑序连续切分会让 5 核退化为**核间接力赛**（加速比恒为 1.00）。
     → 这个反例很容易独立复现：拿 `case_051`，按拓扑序等分切成 5 段分配给 5 个核，
     用官方评估器算 makespan，应得到 ≈607628（与单核几乎相同）；
     再用 `plans_n5/case_051.json` 算，应得到 193319。
3. **索取求解器源码做审计**（本包未附带，按需提供）：`p2_core.py`（图视图、代价模型、
   23 条切分规则、核分配、核内排序）、`p2_run.py`（全量驱动与局部搜索）。
   审计重点建议放在两处历史上出过错的地方：
   - `assign_cores` 的负载增量必须按**整块在各 Pipe 上求和**，若误写成
     "块内单个算子与当前负载之和的最大值"，会让 86 万周期的块看起来只值 4120 周期，
     分配从 5 核退化到 1 核；
   - `CostState.try_move` 必须**全量快照/回滚**（cores、loads、涉及张量、edge_count、edge_bytes），
     否则残留计数会导致局部搜索**接受更差的移动**。
4. **独立复算上界**：用 `LB = max(pipe负载/K, DDR字节/带宽, 关键路径)` 作为乐观下界，
   检查每个用例的"达成率 = 实际加速比 / 上界加速比"。本方案在 21 个用例上达成率只有
   0.27~0.39（均为同步延迟主导的小图），这是公开承认的薄弱区间，欢迎针对此处提出改进。
